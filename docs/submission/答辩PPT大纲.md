本次交付为内容大纲，不包含 PPTX。围绕小型机房和设备间的现场运维展开，主讲现有监测与板载 Agent，手机手册接入、手机语音及 OTA 按实际进度单独说明。

## 一、叙事主线

现场人员需要知道设备是否异常、告警依据是什么、处理后是否恢复。VelaGuard 在 openvela 设备上持续采集并执行本地告警规则，再由板载 Agent 调用只读工具，解释真实数据并生成运行报告。

全场贯穿同一个温湿度监测场景：正常运行、温度越限、本地告警、AI 解释、恢复与报告。接入配置作为前提简述，详细流程放附录。总线扫描是维护工具，不作为产品主入口。

建议封面文案：

- 主标题：VelaGuard
- 副标题：基于 openvela 的 AI 辅助监测网关
- 补充信息：Team Falcons、答辩人、答辩日期

开场口述：我们面向小型机房和设备间的现场运维，让网关持续监测设备，并依据真实数据解释告警、整理运行报告。

## 三、逐页内容设计

### 第 1 页：VelaGuard

使用产品实拍，画面同时能看到开发板屏幕和现场从站。封面只写定位和团队信息，不堆功能、协议和框架名称。

讲述重点：这是独立运行在 STM32H750B-DK 与 openvela 上的现场网关，配置完成后不依赖电脑长期连接。

### 第 2 页：现场运维的问题

用一位负责小型机房的现场运维人员贯穿全场：

- 查看当前状态时，需要理解多个设备的读数和在线情况。
- 出现告警时，需要核对触发阈值、采样状态及相关事件。
- 交接和复盘时，需要整理异常记录与运行统计。

画面：真实应用场景或设备照片，配一组原始读数与对应告警信息。说明这是项目选定的用户场景；未经调研和实测，不写市场规模、节省工时或准确率。

### 第 3 页：产品使用过程

展示三张不同的真实界面：首页状态、告警详情、运行报告。

- 日常查看：已确认点位的实时值、在线状态和异常情况。
- 异常处理：先看到本地规则告警，联网后查看 Agent 解释与数据依据。
- 运行回顾：查看本次运行统计和有效生成的日报，核对来源与时间。

口述补充：当前配置通过上位机或 NSH 的既有流程完成，候选试读后由人单独确认。手机上传 PDF 和从机地址属于后续接入目标，在第 11 页说明。

### 第 4 页：系统架构与职责

架构图只保留与答辩相关的对象：Modbus 从站、openvela 网关、MiMo、MQTT 留档服务与查看端。

网关内部突出两部分：

- 本地业务：采集、统计、规则告警、配置和 LVGL 显示。
- 板载 Agent：基于 ai_agent 执行 Skill，通过只读工具获取事实，整理解释和报告。

讲清模型推理经 HTTPS 调用 MiMo，ReAct 调度和工具执行发生在板端。MQTT 用于现有遥测、告警、状态与已确认点表上报，不承载 AI 请求响应。手机新增服务和 OTA 不挤入本页主图，可在附录展开。

### 第 5 页：本地采集与规则告警

配正常状态和告警状态两张截图，解释从采样到判定的过程：

- 周期采集只使用已确认点表，候选编辑不改变运行中的配置。
- 本地代码依据阈值和真实采样结果判定预警、严重告警及离线。
- 帧统计为通信状态提供依据，界面显示真实读数与采样状态。
- 网络或 AI 不可用时，本地流程继续，显示规则摘要与本地运行报告。

不要将离线状态下的最后一次成功值讲成当前有效读数。告警指示以已实现的屏幕行为为准，不把心跳灯描述为告警灯。

### 第 6 页：板载 Agent 的主动任务

这一页是答辩重点，保留一段工具调用记录和对应屏幕结果。

| 任务 | 板端触发条件 | Skill 与取证 | 可观察产物 |
|---|---|---|---|
| 告警解释 | 告警集合变化 | alarm_interpretation，结合告警上下文和只读统计 | alarm_advice.txt，以及标注 AI 推测的界面解释 |
| 当日日报 | 时钟有效且当天缺少日报 | operations_report，读取运行统计与时间 | daily-日期.md，校验通过后在报告页显示 |

自然语言查数作为补充，展示 modbus_query 与 vg_point_read 的对应关系。强调自定义 Skill 的触发、允许工具和产物，避免只展示一段聊天回答。

解释中的建议属于 AI 推测，规则判定和实际数值应能分别核对。报告必须由实际文件、来源标记及界面共同证明，不能把本地统计报告直接叫作 AI 日报。

### 第 7 页：权限与人工确认

使用一张简明权限表，配工具拒绝记录或人工确认步骤截图。

| 对象 | 权限与限制 |
|---|---|
| 数据查询 | 自定义 C 工具读取运行快照，参数和数量设上限 |
| 解释与报告 | 仅允许受限产物写入，板端校验后展示 |
| 设备处置 | Agent 不改配置、不写寄存器、不清告警、不控制数字量输出 |
| 配置变更 | 确定性校验和人工本地确认，Agent 不参与确认 |

讲述重点：约束落在工具注册和 C 实现中，提示词补充行为说明。工具调用有审计，查询受限流和会话门控约束。具体已覆盖的检查和仍待板验的项目以当前证据为准。

现行 NSH 流程先试读、展示结果，再停下来等待人工确认。手机目标流程不试读，板端确定性校验通过后弹出人工二次确认，确认后直接添加。两种入口的适用范围不要混讲。

- 报告文件与配置存储的校验、失败处理，区分现有保护和待补断电验证。

页面下方说明 openvela 能力落点：LVGL 图形交互、ai_agent 的 ReAct、Skill 和工具机制，以及网络与文件系统支持。

主讲不罗列 MCU 引脚或历史资源预算。公共仓改动放附录，逐项核对已提交、已推送、已开 PR、已合入的实际状态，不用一个 PR 总数代替交付证据。

以真实成果截图结束，保留三项与前文证据对应的价值：

- 配置完成后，网关独立承担现场监测和规则告警。
- Agent 依据只读工具返回的真实数据解释告警。
- 运行报告帮助现场人员回顾状态和异常记录。

收尾口述：我们把持续监测和规则判定放在本地，把 AI 用在告警解释与运行报告上。下一步补齐稳定性验证，并完善手机接入和只读巡检。
