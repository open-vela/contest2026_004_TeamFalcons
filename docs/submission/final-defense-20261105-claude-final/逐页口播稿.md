## 逐页

### 1. 封面（15 秒）

各位评委好，我是叶培林，代表 Team Falcons 汇报我们的参赛作品 VelaGuard。简单说，它是一台跑在 STM32H750B-DK 和 openvela 上的监测网关——本地采集、本地判定，板上的 AI Agent 负责用真实数据做告警解释。

### 2. 一个小机房的一天（32 秒）

先从使用场景讲起。早上七点四十交接班，运维人员打开首页，一屏能看到 14 个点位在线、4 条活动告警、0 个离线，右边这块就是设备上 LVGL 本地渲染的界面。九点十五要接一块新电表，从站地址 3、保持寄存器 0、倍率 0.1，逐项写进候选表。到了十点十二，回风温度升到 83.2 度、越过 80 度阈值，规则在本地判定完成并直接弹出告警页。一分钟后 Agent 读取采集快照，把空调故障、采样异常和通信中断三种可能性分开列出。下午四点半交班，日报已经自动落盘。说明一下，这条时间线是示例流程，越限数值来自台架模拟从站。

### 3. 架构与任务（28 秒）

刚才那一天，背后是一台 MCU 上的四层结构。从上到下是云端与网络、板载应用、openvela 组件、硬件。大家注意右边这六个任务：ai_agent 分配了 32 KiB 栈，vghmi 分配了 48 KiB，采集线程挂在 vghmi 里只有 8 KiB。语音和按键录音优先级分别是 110 和 90。这些优先级和栈大小全部是构建期写死的常量，不依赖运行时动态调整。

### 4. 采集链路与点表闸门（38 秒）

最底层也是最关键的链路，是 RS485 采集。9600 波特、8N1、半双工，每一帧带 CRC 校验，Modbus 主站独占总线，14 个点位一轮扫完。这里有个核心机制叫点表闸门：add、set、del 只能写候选表，apply 必须带 --confirm 参数，由人亲自执行，才会写入已确认表。PPT 上这段是板端实录，14 行 READ 全部 ok=1；你看这里，缺了 --confirm 就返回 need_confirm，退出码 1，写不进去。采集线程点间隔 50 毫秒，读超时 500 毫秒，失败重试一次，一轮结束等 200 毫秒，锁被占用就跳过本轮。

### 5. 写入权限（26 秒）

点表能改，但谁能改、改到什么程度，需要看这张权限表。NSH 能读、能写候选、能 apply --confirm 提交；看板 MQTT 只有四条上行主题；候选 MQTT 只允许 query、open、put、cancel；OTA 只能发 offer；手机只能上传 PDF 和从机地址；Agent 只有五个只读工具。归纳成一句话：提交点表只在本机和 NSH，确认安装只在本机长按 2 秒，控制输出没有任何软件入口。

### 6. Agent 一轮（30 秒）

Agent 是这套权限里最容易被误解的角色，我们单独看一轮。告警进来之后，Agent 走标准的 ReAct 循环：触发、载入 Skill、调 LLM 规划、执行工具调用，结果回填上下文。一轮最多 10 次迭代，每次响应最多调 2 个工具——这两个数字写在 agent_config.h 里，编译期锁定。还有三个兜底上限：60 秒内最多 20 次调用，单轮 300 秒截止，Agent 栈 32 KiB，TLS 握手和 JSON 解析共用这一条栈。右下角是设备上的自然语言问答界面，这里的问答内容是模拟会话。

### 7. 只读边界（28 秒）

Agent 为什么只能读？答案不在提示词里，在 C 代码里。注册层只放了 5 个只读工具，vgpoint、vgcfg、vgdiscover apply 根本没有注册入口。运行层在 C 里做了硬限制：点位查询参数超过 48 字节直接拒绝，输出上限 2048 字节，列表最多返回 12 条。审计层对每次调用计数，写到 agent_tools.log，单文件 64 KiB 轮转。关键在于：提示词可以改，但这三层的限制跟提示词没有关系。

### 8. 端到端时序（26 秒）

把规则、模型和工具串起来，就是这条端到端时序。规则引擎写事件、投递任务，ai_agent 带上 Skill 和工具表请求 MiMo，模型返回 tool_call，板端执行只读工具读采集快照，结果回填，最终输出经 schema 校验后上屏，同时写入 alarm_advice.txt。我们实测了 8 条告警，合计 41.83 秒，其中工具取数只占 1.96 秒——因为读的是内存快照，不占 RS485 总线。

### 9. 断网行为（26 秒）

这条链路依赖网络，那网络断了怎么办？RJ45 拔掉，采集、判定、上屏、事件落盘全部照常。MQTT 断开时告警进 8 条的 RAM 队列，满了丢最旧的，重连后补发，断电就不补了。MiMo 超时就不生成解释和日报，屏幕上保留的是本地规则和真实读数，不会伪造内容。从站离线的判定逻辑是 8 个样本里失败 5 次，一次成功采样就恢复。

### 10. 三个问题（28 秒）

以上是正常路径。接下来讲三个把我们卡了很久的问题。第一个，TLS 报 -0x4380，查到根因是 SDRAM 奇地址复制被编译成了非对齐 LDR 指令，而 H750 的 FMC 不支持非对齐读取。nuttx 里禁用非对齐访问之后，155 次探测零错误。第二个，RS485 方向引脚释放晚了 13 毫秒，0 毫秒从站 274 次通信只成功 38 次；把 DIR 切换挪到 TX 完成中断里，649 次全部成功。第三个，按键录音在 STOP_RECORD 的时候把 clip 给清掉了，ASR 拿到的是空数据。改成只取消路径清理、保留 clip 之后，3 秒录音正常返回 HTTP 200。

### 11. 一次 OTA（34 秒）

修完这些底层问题，固件更新本身也要同样严谨。OTA 从一条 offer 消息开始：MQTTS 8883 端口，订阅 offer，发布 status、result、confirm，控制消息九个字段、不超过 1536 字节。固件镜像走 HTTPS 下载，支持 Range 续传，先取 512 字节的 manifest 做初步校验，再流式下载到 eMMC。校验一共五层：TLS 传输、清单 CRC、ECDSA 签名、流式 SHA-256 和回读比对。到达 READY 状态后，必须在本机长按 2 秒确认，5 项联锁全部通过才写 pending BCB。重启后由 boot stub 擦写 B 槽，BCB 做了两份各 4096 字节。B 槽自检失败 trial 加一，三次后自动回滚到 A 槽。

### 12. 行业场景（22 秒）

这套机制不只服务一间机房。小型数据中心、连锁网点、基站、园区配电间——共同点是设备不多、经常无人值守、网络不一定稳定、出了告警需要有人能解释。同一套固件，换一份点表就能适配：本地规则、AI 解释、权限矩阵、OTA，全部跟着走。目前单网关上限 32 个点位，台架跑了 14 个点位、7 个从站。

### 13. 性能与资源（22 秒）

最后把性能摊开。一次告警解释平均 5.23 秒，8 条合计 41.83 秒，其中模型推理占了 95%，工具取数只有 1.96 秒。语音首播中位数 18.4 秒，30 条里 28 条在 30 秒预算以内。Flash 占用 1.13%，静态 SRAM 占用 69.22%。显示性能方面，60 秒窗口内的提交次数从优化前的 438 次降到了 24 次。
