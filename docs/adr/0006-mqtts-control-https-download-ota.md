# OTA采用MQTTS控制与HTTPS固件下载

状态：已确认设计，待实现和验收。

日期：2026-10-18。来源为用户在本次会话中确认的方案，替代 [ADR 0005](0005-mqtt-only-pull-based-ota.md)。

## 决策与理由

MQTTS负责升级通知、设备接受状态、下载/安装进度、自检确认和结果；HTTPS负责固件镜像下载。升级服务提供受控下载地址、目标型号、版本、大小、摘要和签名信息。板端校验通知与本地升级条件后，流式下载到eMMC，不要求整份镜像进入RAM。

将控制消息与文件传输分开，避免在Broker链路上自定义固件分片请求、排序和缺块重传协议。HTTPS仍需实现流式写盘、完整性检查、失败处理与可选续传；使用Range时必须确认服务端支持，并将暂存内容绑定到同一镜像版本与摘要。

## 安装与恢复

下载阶段不擦写正在执行的QSPI。完整文件的大小、SHA-256、数字签名、目标型号和版本验证通过后，才可记录待升级状态；重启后由片内Flash中的boot stub重新验证并烧写QSPI。新固件须自检并确认，否则进入经验证的恢复流程。

断电、部分烧写、暂存镜像损坏和新固件自检失败均须独立验收。传输协议本身不保证回滚或抗断电；现有启动stub不能当作完整OTA安装器。存储异常、高等级活动告警或供电不稳时按本地策略拒绝升级。采集、告警、界面和日志不依赖OTA服务可用。

## 权限与实现状态

MQTTS和HTTPS验证服务器身份，并分别控制设备与下载权限。受保护的下载地址不完整写入日志；网络加密和通知可信不能代替固件签名校验。MQTT消息仅触发确定性升级流程，设备端Agent没有升级、配置写入或替人确认的权限。

当前四类MQTT上报业务保持，现有明文MQTT、LLM的HTTPS链路和启动stub不构成本方案已实现的证据。MQTTS、OTA订阅/协议、HTTPS下载器、签名校验、安装恢复及资源预算均须按后续任务实现。具体主题与载荷以待制定的OTA协议为准，取消旧 `ota/chunk/*` 固件传输规划。

手机PDF候选配置与语音会话接口独立设计；本OTA决策不开放配置通道。后续同日用户选择MQTT候选传输，见 [ADR 0007](0007-mqtt-candidate-import-with-local-confirmation.md)，仅候选通道取代原先禁止MQTT传候选的范围，人工本地确认保持；AI请求与音频仍不走MQTT。
