# MiMo 三类服务延迟优化：开源调研与实施建议

日期：2026-10-24。性质：研究建议，未实施、未进行新的云端调用或板端测试。

用户已明确 LLM、ASR、TTS 全部保留 MiMo，优化现有链路。本文依据当前板端语音实现讨论应用与传输层优化，保留板载 ai_agent、只读工具、确定性事实校验和 MiMo HTTPS 直连。本文不修改产品范围、AGENTS 或 ADR，也不将现有代码和历史证据等同于新的授权或验收。

## 1. 结论与目标定义

推荐采用现成开源项目已经使用的连接复用、分阶段计时、音频生产与播放解耦、有界队列和取消代际机制，在现有 C 实现内完成适配。开源语音框架可以作为设计参考和主机比较工具，不能直接替代板载 Agent。

可以争取的目标是：在固定硬件、网络、MiMo 服务和回答完整度下，减少本地额外等待，接近接口在该环境中的可观测性能。无法从静态分析证明全局最优，也无法消除服务端排队或保证每轮最低延迟。

分别度量：

- ASR：用户松开按键至最终转写可用；另外记录首个转写 token，不能将它当成最终意图。
- LLM：请求发送完成至首个内容或工具参数增量，以及完整工具调用可执行的时间。工具参数增量不等于可以执行。
- TTS：请求发送完成至首个有效 PCM；另计首个 PCM 至实际播放消费。
- 整轮：松键至首个有效回答音频开始输出、最后一个音频播放完成。
- 质量：识别正确率、工具与事实正确性、完整播报率、取消回收、音频欠载和本地安全环的正常运行。

先以同一网络内主机上的同模型、同音频、同文本、同端点请求作参考，再比较板端。主机参考仍包含网络与服务波动，只能用于定位额外开销，不是纯服务计算时间或严格下界。

## 3. MiMo 接口能力决定可优化范围

### ASR：流式返回不代表录音流式输入

[官方 ASR API](https://mimo.mi.com/docs/zh-CN/api/audio/Speech-Recognition) 将音频放在 JSON 中的 Base64 字段，接受 WAV/MP3；`stream=true` 描述的是 SSE 结果返回。[调用指南](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/multimodal-understanding/Speech-Recognition) 的样例仍先读完整音频。

因此，公开资料不足以证明当前端点支持实时分块音频识别。不能将结果流式开关当作边录边识别，也不能保证用 HTTP chunked 上传就能让模型提前开始计算。现有实现需要最终音频长度生成 WAV 头和 Content-Length。

可先优化连接准备、录音尾部处理、Base64 与上传效率，并对比结果流式与非流式是否实际改善最终转写时间。只有最终文本确认后，才确定设备与点位并触发 Agent。本次不将按键模式扩展为持续 VAD 或全双工监听。

### TTS：支持 PCM 流式输出，首先验证实际端点的分块行为

[官方 TTS 指南](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/multimodal-understanding/speech-synthesis-v2.5) 声明 `mimo-v2.5-tts` 预置音色支持低延迟流式，建议 `pcm16`，样例为 24 kHz、16 位单声道。音色设计和克隆模型的流式能力不能与它混同。

当前请求已经使用 `mimo-v2.5-tts`、预置音色、`pcm16`、`stream=true`。缺口在本地：完整收集 PCM 后才转换、写 WAV，再调用播放器。历史代码注释还记载服务曾用一个大 SSE 块返回长音频；官方主端点的能力声明不能替代当前 token-plan 端点的实测。

### LLM：已有优化要保留，流式工具参数仍需完整校验

当前语音路径已针对 `mimo-v2.6-flash` 关闭思考、限制输出，并使用精简工具上下文。[官方思考参数说明](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/other/deep-thinking) 说明 `thinking.type=disabled` 的语义。

当前回答由工具事实校验后确定性渲染；它不是把模型自由文本逐字朗读的通用聊天路径。不能照搬 LLM token 到 TTS 的连接，绕过事实校验。保留已经存在的一次模型选工具流程和事实复用；不能将诊断用跳模型开关作为优化成果。

## 4. 当前源码与历史样例揭示的问题

本节为本次读取结果；另有任务并发修改工作区，后续实施需重新核对源码和镜像来源。

1. `packages/ai_agent/src/infra/vela_tls.c` 的受控流式请求独立建立 TLS，发送 `Connection: close`，退出时释放连接；普通请求池没有覆盖此路径。LLM 语音受控请求同样使用该传输入口。
2. 该入口的 `send_ms` 只在写完请求头时记录；`body_ms` 的起点仍在握手结束后，覆盖请求头、请求体、等待首响应与接收。因此两者重叠，不能相加归因；`ttfb_ms` 被置为不可用。
3. `app/velaguard/vg_voice_cloud.c` 的 TTS 接收器累计完整 PCM，之后做重采样与 WAV 文件写入；`vg_voice_round.c` 在 TTS 返回后才调用 `vg_voice_play_file`。
4. `overlaygate-normal1.log` 的历史点查询中，ASR 结束约 3.55 秒，事实完成约 8.10 秒，首次可播放约 17.27 秒；TTS 自报 8.85 秒，TLS 0.76 秒，混合 body 5.62 秒。这表明还有未分解的本地或调度等待，但不能把差值全归给重采样，也不能据单轮保证可省多少秒。
5. 同一日志的语音模型请求约 506 输入 token、20 输出 token，思考关闭。继续压提示词的空间需要按真实请求判断，不能套用后台大提示词的数字。
6. 历史报告记录本批测试走 eth0；告警负载下传输变慢已有观察，显示与网络共享资源的具体根因仍是假设。禁止据此随意提高线程优先级或削弱告警显示。

参考：[现有证据说明](voice-evidence/2026-10-23/bvo14-closeout/README.md)、[历史点查询日志](voice-evidence/2026-10-23/bvo14-closeout/overlaygate-normal1.log)。它们是历史证据，本次没有复测。

## 5. 推荐实现结构

```text
按下录音 ── 采集有界 PCM
    └──── 同时准备前台 HTTPS 连接
松键 ── 收尾及确定长度 ── ASR 上传 ── 最终转写
    ── ai_agent / MiMo 选只读工具 ── 执行及校验事实
    ── 生成完整确定性播报文本 ── MiMo TTS
    ── 增量解码 PCM ── 有界队列 ── 增量转换 ── 播放
          网络接收、转换、播放在有数据后重叠进行
```

### 5.1 共用连接层

- 给受控请求增加前台专用连接所有权，正常完整结束后保留连接；ASR、模型和 TTS 在相同 host/port 下顺序复用。
- 首先验证一条前台连接是否足够。后台不得占用它，也不默认并发开启三个完整 TLS 上下文。
- 录音期间异步预连接；不能让准备连接阻塞录音。用户松键后再等待预热，不能算隐藏等待。
- 池键与真实端点、TLS 配置和配置代际绑定；空闲超时、服务端关闭、半关闭、取消和旧请求必须正确处理。
- 只有 HTTP 消息边界明确且已消费完整响应时才允许复用；截断、解析异常和取消路径应丢弃连接。丢失响应的 POST 不做盲目重放；任何重试需有原预算、播放状态与重复输出约束。
- 按现有实际端点与密钥配对测试；不得为了绕开延迟擅自更换域名或创建 AI 代理。

先验证 TLS 1.2 下 keep-alive 的收益，再分别对照 TLS 1.3 和会话恢复。后两者主要改善需要重连的情况。mbedTLS 3.4.0 [支持说明](https://github.com/Mbed-TLS/mbedtls/blob/v3.4.0/docs/architecture/tls13-support.md) 明确不支持 0-RTT；票据在握手后到达，需调整获取与保存时机，不能仅删除 TLS 1.2 字符串判断。

### 5.2 TTS 首声路径

- 原有 SSE 校验保留，解出音频后立即送入有界队列；转换与播放使用独立应用任务。
- 优先复用当前 NuttX 音频上层的缓冲入队接口。先保持已验证的输出格式，做有状态增量转换，避免完整 WAV 落盘作为正常播放前置条件。
- 初始预缓冲可比较 100/200/400 ms 三档；这些是实验参数。24 kHz 单声道 PCM16 的 200 ms 约为 9.6 KB，额外缓冲空间需纳入全链路预算。
- 每个块绑定会话代际，取消清队列并停止播放；旧请求不能把音频送入下一轮。明确队列上限、背压、欠载和终止标志。
- 逐块验证可以支持提前播放，但后续流可能失败。发生截断时必须记录部分播放失败，不能把已经发声计作完整成功。
- 先用整段文本的单次流式请求测量首块与块间间隔。如果实际端点仍整段延迟，再比较按完整语义句拆分请求；播放上一句时准备下一句，先限制为一个在途合成请求，不引入无界并行。
- 分句方案必须保持原回答的全部事实、异常总数和完整前三项，数字、单位、否定和阈值条件不能被拆断。验证句间停顿与重复播报；不以删减播报内容换取成绩。

### 5.3 ASR 路径

- 保留现有中文参数与有界录音，比较 2/5/15 秒音频下的收尾、编码、上传与最终识别耗时。
- 可比较 SSE 转写输出，但最终业务仍等待识别结束；早到的部分文本只作为中间显示，不提前认定点位。
- 降采样、裁静音或 MP3 输入只有在准确率、音质、编码成本和总耗时对照通过时才采用。不能把服务支持 MP3 推导为板端编码一定更快。
- 在当前文件式 API 下，不承诺录音时上传或识别的完整重叠。若需要研究递增上传，单独验证服务是否接受未知长度请求、是否提前解析，并解决 WAV 长度约束；先不列为主方案。

### 5.4 LLM 路径

- 保持语音请求的思考关闭、精简工具、短上下文、单次模型选择和匹配事实复用，先采集实际输入/输出 token 与调用次数。
- 若对照表明有收益，增加 SSE 工具调用增量解析。只在完整调用结束、JSON 和参数检查通过后执行；首个 token 本身不会缩短事实可用时间。
- 稳定系统提示词与工具定义前缀，记录服务实际返回的缓存命中数据；不假设小请求必然命中缓存，也不盲目添加其他平台的缓存参数。
- 不把重复查询改成过期答案缓存；工具数据仍按当前请求与配置代际取得。
- 背景任务继续遵守前台会话门控。告警状态下的资源竞争另做受控对照，不直接通过提高优先级修改系统行为。

## 6. 网络承载的硬约束

按 8N1 计算，115200 波特率最多承载 11,520 字节/秒，协议开销会使实际更低。

- 16 kHz、16 位单声道录音为 32,000 字节/秒，Base64 后约 42,667 字节/秒。
- 5 秒这样的录音仅 Base64 主体就约 213 KB，在该串口速率下理想上传时间已约 18.5 秒。
- MiMo 示例的 24 kHz 单声道 PCM16 为 48,000 字节/秒，Base64 后约 64,000 字节/秒，高于该串口速率约 5.6 倍。

所以，先在已有 eth0 环境建立优化基线；独立设备可以通过以太网接路由器。若最终部署必须走 ESP8266 的该串口配置，连续 PCM 实时传输不具备带宽条件，需要单独评估传输能力或端点支持的压缩格式，不能靠连接预热解决。本文不提出引脚或电路改动。

## 7. 分阶段实施与验收

| 顺序 | 单个任务目标 | 必须回答的问题 |
|---|---|---|
| P0 | 修正计时并建立主机/板端基线 | 每类服务的等待、上传、接收和本地处理分别是多少；真实端点是否持续返回音频块、支持 keep-alive |
| P1 | TTS 有界 PCM 流式播放 | 能否在收完音频前出声；首块后本地等待是否显著下降；欠载、取消、部分流失败是否正确 |
| P2 | 受控请求连接复用与录音期预热 | 热轮次握手次数是否下降；冷、热和失效重连是否稳定；未完成响应是否绝不复用 |
| P3 | ASR 与 LLM 参数/流式对照 | 最终转写和可执行工具调用是否实际变快，准确率与只读边界是否保持 |
| P4 | TLS 1.3 与票据对照 | 重连时实际省下多少；长期生命周期与服务端票据接受情况如何 |

P0 后可依实测调整 P1/P2 顺序；每次实现只做用户选择的一项。P0 不自动开启后续开发。HTTP/2、HTTP/3、额外云代理和跨提供商路由暂不列入主方案。

所有阶段使用同一批合法问题、固定录音、完整播报文本，并覆盖空闲/告警、冷/热连接、正常/慢响应、取消与断网。分组交错执行，避免把服务窗口变化当成本地优化；探索性每组至少 30 轮，正式比较增加样本、给出分布和失败数，不用少量样本宣称稳定 p99。

新增计时建议：录音结束、源数据就绪、DNS、TCP、TLS、请求头写完、请求体写完、首响应字节、首有效 SSE、首 PCM、事实就绪、转换入队、驱动开始消费、最后音频消费和资源回收。正常与错误路径都记录，阶段互不重叠；不记录凭据与原始音频。

优先判断优化后板端相对主机参考增加多少延迟，以及首 PCM 到实际输出的本地开销。绝对首声预算由 P0 的实测数据确定；不凭开源项目演示承诺本板可达到 1 秒或 2 秒。仅完成提交播放命令不能充当真实首声证据。
