# P1/P2 语音延迟优化交付报告（2026-10-24）

任务：按 `docs/voice-latency-open-source-research-2026-10-24.md` 的五步方案实施 P1（TTS 流式
播放）与 P2 一期（ASR/TTS 连接复用 + 录音期预连接），P3/P4 仅核证不实施。执行历经原会话
实现、接手会话修复与本轮收口；各阶段证据目录见文末索引。

## 结论摘要

- P1 流式播放实现并板端验证完成：TTS PCM 增量解码入有界环，专用播放线程直接 ioctl 驱动
  `/dev/audio/pcm0p`，不再累积 512KB 后经 WAV 文件播放。
- P2 一期实现并板端验证完成：ASR/TTS 语音专用 keep-alive 槽顺序复用，录音期预连接使下一轮
  ASR 免握手；LLM 仍走原线程独立连接（跨线程复用不在本期）。
- 过程中发现并修复七个缺陷（含 TLS -0x4380 根因 FMC 非对齐读取与 TCP poll 误报可写），
  全部有独立证据与回归。
- 最终镜像（`enotconn.sha256`）完整验收通过；唯一残留是出口网关在约 1 分钟内第 8 次新建
  连接时丢弃 SYN，板端按预算如实超时，属环境限制，不影响正常语音流程（每轮 ≤3 连接）。

## 一、延迟对照（P0 基线 vs P1 流式）

计时口径：`play_start` 是 AUDIOIOC_START 成功的应用日志（驱动开始消费），未做外部声学测量；
`first_playable` 在 P0 为文件投递近似、P1 起为播放线程 START 时刻，两者不直接可比，下表用
各自轮内锚点对照。样本量为 1-3 轮/档，轮间服务波动 ASR/LLM/TTS 各 ±3-5s，不足以宣称固定
收益，仅列实测。

| 指标 | P0 基线（point01，99840B 答案） | P1 流式（同问题） |
|---|---|---|
| 首声 | first_playable 24020（投递近似，收齐全部 PCM 后） | play_start 20340（接收结束前 4.66s） |
| 整轮 | 27900 | 25470 |
| 播放启动提前量 | 0（tts_end 后才开始） | 早于 tts_end 4.66-8.5s（pilot2 各轮） |
| 慢轮（body 13.6s） | 30s 预算内无任何音频 | 首声 19280，预算内播出大部分（partial=1 如实记账） |

正式镜像复测（release-accept）：两轮 play_start 21860/17740，早于 TTS 接收完成 5.54/5.56s，
整轮 28110/24030；enotconn 镜像两轮 27830/24000，`complete=1 failed=0 leaked=0`。

预缓冲档位实验（100/200/400ms，1-3 样本/档）：起播差异被服务波动淹没，默认 200ms 维持；
进一步压首声依赖 P2 去握手而非调预缓冲。

## 二、欠载与播放器语义

- 服务端分块节奏决定停顿：真实轮每答案 4-6 次欠载、累计 3.4-6.2s，与 P0 块间隔预测一致。
- 离线确定性裁决（`vgvoice streamtest`，1/4 实时速率喂入）：38-40 次欠载全部经再入队+再
  START 自行恢复，无需升级 STOP 重灌路径，complete=1。
- 取消/截断/超时：播放中取消 940-1260ms 完成回收，`retained_pcm=0 controlled_active=0`，
  无代际泄漏；截断归类 VG_VC_TRUNCATED + partial=1（主机测试覆盖）；已出声的失败轮不报成功。

## 三、连接复用与握手节省（P2 一期）

- 语音槽顺序复用：同轮 TTS 复用 ASR 连接；后续轮次 ASR 经预连接命中热连接，第二轮预连接
  耗时 0ms，dns/tls 相位为热连接值。
- 复用发布规则：仅框架完整（分块终止符/长度满足/干净 EOF）或 sink 提前完成且补排空验证
  通过才保留连接；错误、取消、截断、排空超时一律销毁。已发送的 POST 不盲重放。
- 陈旧连接：排空探活判陈旧后原地重连，连续新建压力中 7 次全部透明恢复（enotconn 镜像）。
- LLM 回归：重构后 LLM 路径独立连接 status=200，主机 `test_tls_stream_upload` 三场景原样
  通过（字节级不变的回归证据）。

## 四、过程中定位并修复的缺陷

| 缺陷 | 根因 | 修复提交 |
|---|---|---|
| 板端三服务 HTTP 400，主机同形请求 200 | 请求快照未初始化，provider 串未终止，发出污染的 X-Model-Provider-Id | ai_agent `7c33205` |
| TLS 握手 -0x4380 间歇验签失败 | 编译器对 SDRAM 非对齐地址生成逐字 LDR（ST ES0392 2.6.4 FMC 限制） | nuttx `45dd33ad936`（FMC 构建统一 -mno-unaligned-access） |
| ttss 诊断路径硬故障 | 嵌套栈帧 33.6KB 超 32KB 预算，返回地址被 PCM 覆盖 | 本仓：PCM 片段 16384→3072 |
| 网络缓冲 127/128 被占用 | ping 原始 socket 被子任务继承，回复积压无人读 | apps `0c8bc59ce`（SOCK_CLOEXEC） |
| 第 8 次新建连接前即套接字分配失败 | 固定 8 个 TCP 槽位被 TIME_WAIT 占满 | 本仓 defconfig：8 预分配+4 增长，上限 32 |
| 快速新建连接第 7/8 次握手 send 立即 ENOTCONN | NuttX TCP poll 对 SYN_SENT 误报 POLLOUT（无写缓冲时 cansend 恒真） | nuttx `5454419b235` + ai_agent `67e8b14`（双层） |

400 的旧密钥推断与 TLS 的未知堆写者假设均已被证据撤回，见各证据 README 的接手复核更新。
TLS 根因另有独立佐证：原排查会话两份失败转储（`../tls-root-cause/pull-dump0.log`、
`pull-dump-p2b.log`）的 in_msg 地址均为奇地址（0xd027efc5 / 0xd02a11b5，
in_buf+13 构造性为奇），复制源恰好非对齐，与 ES0392 机制吻合；当时无法转储的
mbedtls 私有 randbytes 正是损坏所在环节，copy-probe 在 memcpy 后立即比对补齐了判决。

## 五、残留限制与未覆盖范围

1. 出口网关（Windows ICS + fake-ip 代理）在约 1 分钟内第 8 次新建连接时丢弃 SYN：板端等待
   至预算耗尽后如实返回 timeout，无数据损坏、IOB 全额回收。正常语音流程每轮 ≤3 连接不受影响。
2. P0 全量矩阵（冷/热 × 空闲/告警各 ≥30 轮）未执行，挂账为独立任务；本报告不宣称固定整轮
   收益或长期稳定性。
3. P3 结论：本地侧无可回收空间（PDM stop 50ms 为硬件停机握手上限、base64 已流式、TLS 记录
   已 16KB 合并），不改代码。P4：主机探针已确认服务端 TLS 版本，固件侧 TLS 1.3 开关涉及
   apps 公共树全库重编，维持关闭，留作后续任务入口。
4. 跨线程 LLM 连接复用、板端音频新功能不在本期范围。
