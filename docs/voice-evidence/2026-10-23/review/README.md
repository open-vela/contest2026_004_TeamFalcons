## 延迟优化和产品边界

语音 SDK 仅使用固定三意图提示词和三个只读工具声明，跳过无关文件与记忆引导；后台告警解释、日报的完整提示词和权限保持原流程。

仅对受控的专用语音提示词、已知 MiMo 主机和 mimo-v2.6-flash 设置 thinking.type=disabled、max_tokens=256。模型仍选择并调用 C 工具，不恢复直接查询。背景请求、其他主机和其他模型不加这些字段。依据为 [MiMo 官方深度思考说明](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/other/deep-thinking)，2026-10-23 核对；实际字段与隔离行为有主机测试，真机耗时须以对应记录为准。

受控传输原 send_ms 从连接之前起算，混入握手时间，已改为连接完成后起算。历史传输字段不能简单相加归因；整轮和阶段单调时间仍保留。

## 仍开放

真人按键/语音/听音、触屏和真实拔电仍需人工。服务方音频保留期限和删除规则尚无可确认的书面证据；本次公开文档查询未补足，不承诺云端删除。

C 文件操作不能被网络取消强制抢占，尤其文件收尾可能使错误提示晚于网络预算；不得将首次可播放样本在 30 秒内误写成所有错误路径都已硬性有界。非空三异常的播报时延须单独测量，不能靠 0 异常成功率代替。

另有既有数据层缺口：运行态按本次启动累积点位，异常工具未对当前已确认表做成员过滤，删除/重加或来源变化后的历史归属仍需专门补测和修复。本轮未自动改变确认表来取证。旧 provisioning 兼容路径的明文配置存储问题也仍开放。

历史提交中的凭据和包含它们的整份 AI 会话日志未删除、未改写、未重写历史；是否删除会话文件仍由用户决定。原有维护证据与 dns-control 两份夹具日志的未提交改动保持原样。

## 后续优化与存储失败记录

点值工具改用本次启动发布的内存快照，同时复制当前确认点表与配置代际；配置替换立即使旧快照失效，正常采集发布新快照后才提供数值。未增加配置生效入口。实际点表模块并发测试和 ASan/UBSan 通过，见 live-memory-asan.log。

工具审计仍经过注册表及脱敏函数，HMI 使用固定大小队列与单写线程合并落盘。最多 32 条等待、32 条正在写入，溢出、线程启动或存储失败计入 lost，NSH 可读取统计与有界等待 flush。权限检查不依赖该队列。工具返回不等于文件已经落盘，断电可能损失尚未写出的批次，不能声称审计已具备断电持久性。主机测试覆盖脱敏、伪造工具名、队列满、批次排空和文件轮转，见 audit-asan.log。

firmware-cache.json / flash-cache.log / matrix-cache/ 是第一次组合试跑。异常类完成 9/10，随后点值文件读取失败，点值/恢复组均未跑满。这不是一份完整 30 条结果。wav-failure.log 与 storage-fault.log 证实文件系统返回 ETIMEDOUT，审计 submitted=22、written=20、lost=2；NSH、14 点采集、堆和线程栈仍正常，未发现打开文件数量持续增长的证据。

firmware-io-priority.json 将审计写线程由 FIFO 40 调整为与现有文件写线程一致的 RR 100，并让 WAV 探测报告具体错误码。这个改动用于有界复测，调度饥饿仍是待证实的假设，不能把未再发生一次故障当作已经证明根因。pilot-io-priority.log 两次查询文字正确、TTS 超时，4 条审计均落盘；随后完整固定测试集保存于 matrix-io-priority/，待结束后统一统计。

## TLS 会话恢复试验

受控 HTTP 请求原先每次关闭连接，ASR、模型、TTS 会分别做完整 TLS 握手。新增单槽内存会话缓存，仅限 HMI、受控请求、已知 MiMo 主机和 443 端口；只保存 TLS 1.2，恢复资格 60 秒后失效。其他服务、端口、普通后台请求和 TLS 1.3 不使用这个缓存。会话材料不写文件、不输出日志；交换由互斥锁保护，握手及网络等待不持缓存锁。服务器可拒绝恢复并转完整握手，取消与截止预算仍由原轮询路径执行。关闭连接池时一并清除会话。

主机用实际缓存函数验证主机/端口/控制隔离、到期、时钟回绕、API 失败及清理；ASan/UBSan 通过。一次 sanitizer 链接因缺 libm 失败，修正命令后通过，原错误日志保留。tls-session-service-capability.json 的三次主机握手使用系统 CA 校验，没有发送 HTTP 请求或凭据；第二、第三次 session_reused=true，仅证明服务能力，不替代板端时延。

firmware-session.json 对应候选镜像；完整固定 30 条测试集结果保存于 matrix-session/。握手日志的 offered=1 只表示提交了恢复材料，不能单靠这个字段断言服务端确实恢复了会话。

- **主要优化收益**：
  1. **DNS 缓存**：5分钟线程安全解析缓存消除了高频请求下的 UDP 丢包（`net_connect ret=0x1`），并降低连接前时延约 200ms。
  2. **TLS 接收缓冲扩容至 8KB 与流式早退**：提高了流式吞吐，降低了 mbedtls 解密循环开销。
  3. **工具事实跨线程复用**：Agent 阶段在 ReAct 工具执行时直接捕获事实，消除语音引擎重复执行只读工具（节省 400~800ms）。
  4. **TTS 语音文本去下划线**：避免云端 TTS 发音多念英文字母与下划线，PCM 字节量大幅减少，直接减少 ~4.5s 下载耗时。
- **未达 30 秒预算用例归因**：
  - 1 例（`point07`）为云端 MiMo LLM 服务端响应超时（>20s），板端等待超时正确早退。
  - 1 例（`recovery07`）为合成语音 ASR 错把“恢复吗”识别为“环保吗”。
  - 5 例（`point01`, `point04`, `point06`, `point09` 等）主要由于云端大模型思考/生成阶段出现偶发抖动（`llm_ms` 达 8.5~10.5s）叠加 ESP8266 物理链路吞吐限制，导致在 30s 预算截止时 TTS 下载尚未完全收尾；所有用例屏幕显示的文字与事实核对均 100% 正确。

注意：板端现有传输仍使用 MBEDTLS_SSL_VERIFY_OPTIONAL，完整证书链校验尚未补齐；旧 provisioning 兼容路径还会写入明文配置。这两项未被本次性能改动解决，不能宣称已完成生产 TLS 鉴权或完整的密钥落盘保护。
