# ASR/TTS 板端接入合同

本文件是 BVO-07 和 BVO-11 的实施依据。所有数值来自本轮官方文档与主机实测，板端能力来自当前源码只读核对，未在设备上验证。主机完成的转换不代表板端已支持。

## 1. 前提

| 项目 | 现状 |
|---|---|
| 采集格式 | 16000 Hz、16 位、单声道 PCM，最长 15 秒（BVO-03/BVO-05 已验证） |
| 落盘格式 | `/data/velaguard/voice/clip.wav`，WAV 头写 2 声道，单声道样本复制到左右（`app/velaguard/vg_voice.c:356` 起） |
| 回放格式 | 16000 Hz、16 位、双声道 WAV，NxPlayer 播放（BVO-04/BVO-05 已验证） |
| 传输实现 | `packages/ai_agent/src/llm/llm_proxy.c`，整包构造请求，整包读取响应，HTTP/1.1，`Connection: close` |
| TLS 连接池 | `CONFIG_AI_AGENT_TLS_CONN_POOL_SIZE=1`，同一时刻只有一条 TLS 连接 |
| 端点配置 | 主机名运行时配置，路径默认 `/v1/chat/completions` |

## 2. ASR 上传合同

### 2.1 报文形状

```json
{
  "model": "mimo-v2.5-asr",
  "messages": [{
    "role": "user",
    "content": [{
      "type": "input_audio",
      "input_audio": { "data": "data:audio/wav;base64,<BASE64>" }
    }]
  }],
  "asr_options": { "language": "zh" }
}
```

- 端点：`POST {MIMO_BASE}/v1/chat/completions`，`MIMO_BASE` 必须是与密钥配套的域名。
- 鉴权：`Authorization: Bearer <key>` 或 `api-key: <key>`，两种都可。板端现有代码用 Bearer，可沿用。
- 音频必须是完整文件，服务端没有分片上传或边录边传接口。
- 只支持 wav 和 mp3。板端用 wav，MIME 为 `audio/wav`。
- 采样率与声道服务端自行处理：实测 8 kHz 单声道与 44.1 kHz 双声道都得到相同文本。因此板端不必为格式做重采样，但必须控制体积。

### 2.2 体积

| 方案 | 音频字节 | Base64 字节 | JSON 请求体 |
|---|---|---|---|
| 15 秒，16 kHz，单声道 | 480,044 | 640,060 | 约 640.5 KB（实测 640,512） |
| 15 秒，16 kHz，双声道（现有落盘格式） | 960,044 | 1,280,060 | 约 1.28 MB |
| 15 秒，8 kHz，单声道 | 240,044 | 320,060 | 约 320 KB |

官方上限是 Base64 字符串 10 MB，本项目 15 秒上限远低于该值，限制来自板端内存而不是服务端。

结论：不能直接上传现有的双声道 WAV。要么另写一份单声道 WAV，要么在编码时只取一个声道。

### 2.3 内存

当前 `llm_proxy.c` 的路径是 `cJSON_PrintUnformatted` 生成完整 JSON 字符串，再一次 `proxy_conn_write` 发出。按 15 秒单声道估算：

| 项 | 大小 |
|---|---|
| PCM 原始缓冲 | 480 KB |
| 单声道 WAV 文件 | 480 KB（可只在 eMMC，不占堆） |
| Base64 字符串 | 640 KB |
| JSON 请求体字符串 | 640 KB |
| cJSON 树与临时拷贝 | 数十 KB 起 |
| 峰值合计 | 约 1.7 至 1.8 MB |

BVO-05 记录的开机空闲堆约 837 KB（`used=836632` 时为 1008 块）。即使把 PCM 缓冲放到 eMMC，仅 base64 加 JSON 两份字符串就已经超过 1.2 MB。现有整包构造方式在 15 秒上限下不可行。

可选方案，按推荐顺序：

1. 文件后备加流式发送。录音已经写入 eMMC，读取时按 3 字节一组编码成 4 字节 base64，分块写 socket，峰值缓冲控制在 64 KB 以内。需要支持分块写入或预先算出 Content-Length。
2. 降到 8 kHz 单声道再上传。请求体约 320 KB，仍需要至少 640 KB 的字符串峰值，接近但仍在现有堆的边界，风险高。
3. 缩短上限到 5 秒。不推荐，会改变已确认的 15 秒交互合同。

方案 1 属于 BVO-07 的传输改造，本轮不实现。

### 2.4 响应

| 项 | 值 |
|---|---|
| 成功响应大小 | 447 至 648 字节（实测） |
| 关键字段 | `choices[0].message.content`，空识别为空字符串 |
| 计时字段 | `usage.seconds` 为音频秒数向下取整加 1 |
| 失败响应 | `{"error":{"code":"400","message":"..."}}`，113 字节 |

响应很小，现有整包读取方式可以直接复用。

## 3. TTS 返回合同

### 3.1 报文形状

```json
{
  "model": "mimo-v2.5-tts",
  "messages": [
    { "role": "assistant", "content": "<待播报文本>" }
  ],
  "audio": { "format": "pcm16", "voice": "冰糖" }
}
```

- 待合成文本必须放在 assistant 消息，放 user 会被当成风格指令。
- 可选 user 消息用于语气控制，首版不需要。
- `stream: true` 时返回 SSE，每个分片的 `choices[0].delta.audio.data` 是一段 base64 PCM。

### 3.2 返回格式

| 格式 | 实测结果 |
|---|---|
| wav | RIFF/WAVE，24000 Hz，1 声道，16 位，44 字节头 |
| pcm16 | 无头 PCM16LE，24000 Hz，1 声道 |
| mp3 | MPEG 帧同步，板端无解码器，不建议 |

板端回放是 16000 Hz 双声道。TTS 返回 24000 Hz 单声道，必须转换：

- 重采样 24 kHz 到 16 kHz，比例 3:2。可以用简单的 3 抽 2 线性插值，语音质量足够，但要在 BVO-11 听音确认。
- 单声道复制到左右声道，与现有 `vg_voice.c` 的写 WAV 逻辑一致。
- 另一种选择是把 SAI 播放采样率配到 24 kHz，避免重采样。当前播放链路固定 16 kHz，本轮未验证 24 kHz 是否可用。

### 3.3 体积与缓冲

| 场景 | PCM 字节 | JSON 响应体 |
|---|---|---|
| 6.08 秒 WAV | 291,884 | 389,667 |
| 6.72 秒 PCM 非流式 | 322,560 | 430,567 |
| 6.40 秒 PCM 流式 | 307,200 | 418,172（23 个分片） |
| 8.32 秒 WAV | 399,404 | 533,027 |

现有 `llm_proxy` 不解析 SSE，会把整个 SSE 正文缓冲到内存再处理，因此流式在板端拿不到低延迟收益，只是把 418 KB 一次性读进来。峰值约为 SSE 正文 418 KB 加解码后的 307 KB，接近 725 KB，与 ASR 同样超出安全区间。

建议路径：

1. 用 `stream: true` 加 `pcm16`，逐分片解码 base64，写入 eMMC 临时 PCM 文件，峰值只需单个分片的缓冲（实测每片约 13 KB base64，解码后约 10 KB）。
2. 播报前把临时 PCM 转成 16 kHz 双声道 WAV，交给 NxPlayer。
3. 若 BVO-07 实现不了逐分片处理，退化为非流式整包，则必须先把响应写入文件再解码，不能同时在内存里保留 JSON 与 PCM。

播放缓冲至少需要两个 20 ms 的 16 kHz 立体声块（每块 1280 字节），双缓冲，避免欠载。BVO-04 已记录 SAI 欠载与 FEIF，新增解码任务不能加重播放线程的阻塞。

## 4. 传输层

| 项目 | 服务端实测 | 板端现状 | 差距 |
|---|---|---|---|
| TLS 版本 | TLS 1.3，TLS_AES_256_GCM_SHA384 | mbedTLS，具体版本未核 | 需要确认支持 TLS 1.3 或至少 1.2 |
| ALPN | 服务端提供 h2，HTTP/1.1 也可用 | HTTP/1.1 | 无差距 |
| DNS | 正常解析 | netinit 提供 DNS，语音路径未验证 | BVO-07 需实测 |
| 连接复用 | 支持 keep-alive | `Connection: close`，每次新建 | 可保持现状，代价是每次重新握手约 70 至 170 ms |
| 并发 | 未测 | TLS 连接池为 1 | ASR、TTS、Agent 只能串行 |
| 请求体 | 无特殊要求 | 整包构造 | 大请求体需要流式改造 |
| 响应体 | Content-Length 或 chunked | 两者都能识别（`http_body.h`） | 无差距 |

## 5. 超时、取消、限流、重试与清理

| 语义 | 建议 | 依据 |
|---|---|---|
| 总预算 | 从松手或 15 秒自动提交起算 30 秒 | 执行方案第 2 节 |
| ASR 超时 | 8 秒 | 实测 15 秒音频 1.25 秒，留 6 倍余量 |
| TTS 首包超时 | 8 秒 | 实测流式首包 0.44 秒，非流式首字节 1.5 至 3.0 秒 |
| TTS 整段超时 | 15 秒 | 47 字实测 3.2 秒 |
| 取消 | 关闭 socket 即视为取消 | 服务端无取消接口，已发出的请求仍会计费 |
| 429 | ASR 不自动重试，提示重录；TTS 最多重试 1 次 | 现有 `AGENT_LLM_MAX_RETRIES=3` 对语音过长，会挤占 30 秒预算 |
| 网络错误 | 不重试，直接进入失败分支 | 重试会叠加 TLS 握手与上传时间 |
| 录音清理 | 上传结束立即删除 `clip.wav`，成功失败取消都删 | 执行方案要求原始录音只供当次识别 |
| TTS 清理 | 播报结束或失败后删除临时 PCM 与 WAV | 同上 |
| 凭证 | 只从加密配置读取，不进日志、串口、UI | 现有 `vgprovision` 机制 |

## 6. 云端数据保留

| 问题 | 结论 |
|---|---|
| 是否上传录音到云端 | 是，ASR 必须上传完整音频 |
| 云端保留多久 | 未知。隐私政策只写按目的必需期间保留，无固定天数 |
| 是否用于训练 | 文本明确未经同意不用于训练；音频未被该条款覆盖，未知 |
| 存储位置 | 中华人民共和国境内 |
| 删除渠道 | 通过 privacy.mi.com/support 申请，无 API |
| TTS 音频有效期 | 响应 `expires_at` 恒为 null，未知 |

产品文案只能承诺本机不保留录音与对话，不能承诺云端不保留。

## 7. 下游任务

### BVO-07 必须完成

1. 请求体流式发送，支持从 eMMC 文件读取并分块 base64 编码，峰值缓冲不超过 64 KB。
2. 响应流式读取，至少支持按 SSE 分片回调，供 TTS 边收边写文件。
3. 真实测量板端 DNS、TCP、TLS 握手、上传、首字节、下载耗时，验证 30 秒预算。
4. 取消语义：关闭 socket 后连接与缓冲全部回收，旧结果按 generation 丢弃。
5. 确认 TLS 连接池为 1 时 ASR、TTS、Agent 的排队顺序，避免语音请求被后台任务长期占用。

### BVO-11 必须完成

1. 24 kHz 到 16 kHz 重采样与单声道转双声道，或验证 24 kHz 直接播放。
2. TTS 分片拼接与临时文件生命周期管理。
3. 空识别不调用 Agent，直接提示重录。
4. TTS 失败保留文字，仅重试播报。
5. 静音开关跳过 TTS，且不发起 TTS 请求。
6. 点位 ID 的同音归一，至少覆盖零幺与零一。
7. 听音确认音色、语速与数字读法。

## 8. 明确不做

- MQTT 不承载 ASR/TTS 请求、响应或音频分片。
- 不实现代理服务器中转语音。
- 不做板端离线 ASR/TTS。
- 不在本轮实现上述任何代码。
