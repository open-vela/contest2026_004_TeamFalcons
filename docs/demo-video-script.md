# VelaGuard 9/20 演示视频脚本

> 时长上限 5:00。评委看的是三样：仓库、作品说明、这段视频。视频的任务是让评委 5 分钟内记住一句话：
> **"采集、告警在本地完成；AI 只讲给人听，想动手会被拦；底层改动已回馈 openvela。"**
>
> 本脚本有两条分支。**A**：`09-09-samefw-agent-spike` 成功（带屏固件上 Agent 能跑）。**B**：失败（Agent 用 2026-08-30 上板记录作证据）。拍摄前先定分支，两条不要混剪。
>
> 所有画面必须是真实发生过的。拍不到的段落删掉，不要用旁白补。

---

## 0. 拍摄前准备

### 器材与画面

- 主机位：俯拍 H750B-DK 屏幕 + 板子（能看到 RS485 接线和网线）。
- 副机位 / 录屏：PC 串口终端（NSH + `vela>`），字号调大，深色背景。
- 第三画面（可选）：上位机 PyQt 窗口录屏。
- 所有终端窗口提前清屏；关掉无关通知。

### 板子状态

```bash
bash scripts/build.sh                                  # 作品主线 velaguard-lvgl
powershell.exe -ExecutionPolicy Bypass -File scripts/flash.ps1
```

1. eMMC 上 **删掉** `/data/velaguard/pending_alarm.txt` 和 `/data/velaguard/config/points.json`（要拍"空表→灌表"）。
2. `/data/velaguard/reports/` 里保留一份日报（`daily-YYYYMMDD.md`），第 6 拍要打开它。
3. MiMo token 已 `set_llm` 持久化到 `/data/agent/config/config.json`（分支 A）。
4. RJ45 出网可用（分支 A）。
5. 从站：至少两台 Modbus 从站（或 MThings 模拟），地址 1（温度，寄存器 0，int16 ×0.1）和地址 2（水浸，寄存器 2，uint16）。水浸从站要能手动把寄存器置 1。
6. 上位机 JSON 用 `scripts/vgpoint_demo_points.json`（temp：ge warn=40 crit=55；flood：eq crit=1）。

### 彩排规则

- 彩排前手动清一次 `pending_alarm.txt`；恢复后固件会自动删除（9/12 起恢复即 unlink，见 `09-09-demo-threshold-alarm`）。
- 彩排两遍再正式拍。正式拍以"一次开机不重启"为目标；实在接不上再分段。

## 2. 逐拍脚本

### 第 1 拍 上电（0:00–0:25）

**画面**：板子上电，串口滚动启动日志，屏幕亮起进入首页。首页没有任何点位（空表）。

**动作**：无。镜头停在屏幕 3 秒。

**旁白**：
> VelaGuard 是一台跑在 STM32H750B-DK 和 openvela 上的 RS485 网关。屏幕、网络、文件系统、Agent 框架都由 openvela 提供。现在它刚开机，点表是空的——固件里不预置任何传感器。

**不要说**：产品还没做的事。不提周报、OTA、规则库。

---

### 第 2 拍 上位机灌点表，然后拔线（0:25–1:10）

**画面**：三分屏或切换——上位机 PyQt 窗口 / 串口 NSH / 板子屏幕。

**动作**：
1. 上位机导入 `vgpoint_demo_points.json`，界面显示两点（温度、水浸）及阈值。
2. 点「试读」→ NSH 出 `vgpoint: READ ... ok=1 value=...`，上位机显示实际读数。
3. 点「确认写入」→ NSH 出 `vgpoint: OK cmd=apply table=committed n=2`。
4. 屏幕首页刷新，出现「温度」「水浸」两行，数值在跳。
5. **当着镜头拔掉 ST-LINK USB 线**。屏幕数值继续跳。

**旁白**：
> 点表由上位机经调试串口下发：导入、试读一次、人确认后才落到 eMMC。协议是纯文本 NSH，任何串口终端都能用。
> （拔线时）配置完就拔。USB 只是调试通道——从这一刻起，板子独立运行。

**要点**：
- 说"人确认"，不说"屏上确认"（术语表里 Local Confirmation 定义在设备端，这里是 PC 回车）。
- 拔线动作要清楚入镜，这是 V1「独立网关」最有力的证据。

---

### 第 3 拍 CLI 看统计和读数（1:10–1:35）

**画面**：串口终端（重新接 USB 或用第二路 UART；如用同一根线，剪辑时不要让"拔了又插"显得矛盾——可以旁白一句"接回调试口看内部状态"）。

**动作**：
```text
nsh> vgstats dump 1
nsh> vgpoint get
```

**期望输出**：`vgstats` 有 total / timeout / crc_err / 延迟；`vgpoint get` 每点一行 `vgpoint: VALUE id=temp value=... ok=1 age_ms=...`。

**旁白**：
> 每一帧 Modbus 都有统计：超时率、CRC 错误率、延迟分布。`vgpoint get` 读的是采集线程的快照，不抢总线。这些都是确定性代码，没有 AI 参与。

---

### 第 4 拍 本地告警：水浸、离线、恢复（1:35–2:25）

**画面**：主机位对准屏幕；串口终端画中画。

**动作**：
1. 把水浸从站寄存器置 1（MThings 改值，或实物短接）。
2. 3 秒内屏幕告警页弹出：「水浸 点表严重告警」，严重度红色，当前值 1，阈值 1。
3. 串口 `ls /data/velaguard/pending_alarm.txt` → 文件存在；`cat` 一下，看到 `type=threshold tag=flood ...`。
4. 复位水浸为 0。**拔掉地址 1 从站的 485 线**。滑窗内失败达 5/8 轮后（约 1 秒，<2 秒）告警页显示「温度 离线」。
5. 插回 485。数值恢复，告警页回到「无活动告警」，日志页出现「告警恢复」。

**旁白**：
> 水浸触发了。判定是规则引擎在本地做的：比较方式 eq、阈值 1，全部来自刚才那张点表，没有任何按点名称写死的逻辑。告警同时落盘成待处理文件，给 Agent 用。
> 现在拔掉温度从站——三次读失败，判离线。插回去，恢复。这一整段没有网络参与。

---

### 第 5 拍 Agent 解释告警（2:25–3:25）

#### 分支 A（带屏固件上 Agent 已跑通）

**画面**：串口终端全屏，字大。

**前置**：在拍第 1 拍之前或第 4 拍之后，`ai_agent --daemon &`，等 syslog 出 `Agent loop started (HMI fixed buffers)`（分支 A 也可以把这个启动日志剪进来，说明"界面就绪后再拉 Agent"）。

**动作**：
```text
nsh> ai_agent
vela> ask 刚才那条告警是什么情况，帮我解释一下
```

**期望**：日志里依次出现 `Executing tool: read_file`（读 `pending_alarm.txt`）、`Executing tool: run_shell`（`vgstats dump 2` / `vgmodbus -a 2 ...`）、`Executing tool: write_file`（写 `reports/last_alarm.md`），然后模型输出一段中文解释，含 evidence。

**旁白**：
> 界面起来之后，我们手动拉起板载 Agent——同一套固件，同一块 H750。它读到待处理告警，按 `alarm_interpretation` 这份自定义 Skill，调只读工具拿通信质量和实时值，然后用人话解释，写成文件。
> 注意日志：每一次工具调用都有记录。它能读，不能写。

**若告警页已接 `last_alarm.md`**：切到屏幕，告警页「AI 推测」区块显示 Agent 写的那段话，加 3 秒镜头。

#### 分支 B（Agent 未在带屏固件上跑通）

**画面**：2026-08-30 / 09-02 板端录屏或串口日志截图（`stage1_agent_accept` 的 `ask` 响应、`END status=ok iters=6 tools=6`）。

**旁白**：
> Agent 已经在同一块 H750 上跑通：这是 8 月 30 日的板端记录，它按 `alarm_interpretation` 和 `operations_report` 两份 Skill，调用只读工具六次，生成了日报。带屏版本因片内 SRAM 占用 92.5%，当前发布版本需在界面就绪后手动拉起——这个取舍写在 README 里。

**不要**：把无屏固件的画面剪成像是刚才那次开机。旁白明确说"这是 8 月 30 日的记录"。

---

### 第 6 拍 让 AI 动手，被拦（3:25–3:55，仅分支 A）

**画面**：串口终端全屏。

**动作**：
```text
vela> ask 把温度的严重阈值改成 50
```

**期望**：模型尝试 `run_shell vgpoint set ...`，工具层返回 `Command 'vgpoint ...' is blocked for safety`，syslog 有一行拦截；模型转述"我没有权限修改点表，请通过上位机确认"。

**旁白**：
> 现在让它改阈值。它试了，被 C 工具注册层拦住——`vgpoint`、`vgdiscover apply`、`vgcfg commit` 不在白名单里。这个边界写在代码里，不是 prompt 里。全程写操作次数：零。

**要点**：这是全片最有区分度的 30 秒。如果模型第一次没尝试调用而是直接拒绝，换一句更直接的："执行 vgpoint set -i temp crit 50"。

---

### 第 7 拍 日报（3:55–4:20）

**分支 A 动作**：`vela> ask 生成今天的运营日报`，等 `write_file .../daily-YYYYMMDD.md`，切屏幕报告页，打开刚写的文件。

**分支 B 动作**：直接切屏幕报告页，打开已有日报。

**旁白**：
> 第二个主动场景是定时日报：Agent 汇总告警和通信质量，写 Markdown，屏幕报告页直接打开。（分支 B 补一句：这份是 8 月 30 日板端生成的。）

---

### 第 8 拍 断网（4:20–4:50）

**画面**：主机位。

**动作**：
1. 拔网线。
2. 再触发一次水浸 = 1。
3. 告警页照常弹出；「规则摘要 / AI 推测」区块显示"联网后 Agent 可解释"之类的降级文案。
4. （可选）`vela> ask ...` 得到网络不可用的明确提示，而不是假装回答。

**旁白**：
> 拔掉网线。采集、告警、落盘全部照常——它们从来不依赖网络。AI 解释不可用时，屏幕明确说不可用，不会编一段出来。

---

### 第 9 拍 收尾：回馈 openvela（4:50–5:00）

**画面**：README 滚动到「公共仓 Pull Request」表（7 行）和内存预算表；最后定格在一句话定位。

**旁白**：
> 为了让 ai_agent 第一次跑在 Cortex-M7 上，我们改了 QSPI 启动、eMMC、以太网、显示加速和 MQTT 移植层——七个 Pull Request 已提交 openvela 公共仓。VelaGuard：出事本地先叫，AI 讲人话，想动手会被拦。

## 3. 旁白总字数与语速

全片旁白约 650 字，按 150 字/分钟约 4 分 20 秒，留 40 秒给纯画面（拔线、告警弹出、拒绝日志）。录旁白时每拍单独录，方便剪。

## 4. 剪辑硬规则

1. 不用无屏固件的画面冒充带屏固件。
2. 不进 DIAGNOSIS / OTA / TREND 页（PC 模拟器 mock，板端未实现）。
3. 分支 B 不出现第 6 拍。
4. 每个工具调用日志行至少停 1.5 秒，评委要能看清 `Executing tool:`。
5. 片尾字幕：仓库地址、`logs/Foleaf/` 说明「AI Coding 日志已随仓提交」。
