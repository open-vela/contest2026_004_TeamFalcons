# VelaGuard MQTT 候选接入协议草案 v0.2

日期：2026-10-18。状态：设计草案，代码、主题、鉴权及界面均未实现或板验。

用户选择MQTT传输候选，异常与恢复由开发助手设计。按用户最新更正，手机接入不试读；远程配置状态只在手机显示，板端配置校验通过后仅弹出人工二次确认，确认后直接添加。最近一次修改的版本按最新编辑的候选理解，具体版本号由任务维护。与 [ADR 0007](adr/0007-mqtt-candidate-import-with-local-confirmation.md) 配套。

## 1. 范围与现状

手机通过受鉴权的HTTPS接口一次提交PDF和从机地址；云侧提取候选，通过MQTT发送到绑定的网关。板端确定性服务负责配置校验、合并预览和本地确认，不对候选试读，板载Agent不参与配置。确认添加后才加入正常采集；添加成功只表示配置生效，不代表从站已响应。实际在线状态和读数由之后的正常采集更新，不生成确认前的采样值。

当前固件只有四类MQTT上报，没有候选下行订阅。新增接口实施前仍按 [NSH协议](velaguard-host-nsh-protocol.md) 操作。当前NSH的人工确认由操作流程与 `--confirm` 参数共同表达，固件尚不检查是否试读过及试读对应哪个版本；不能把本设计写成既有能力。

本次只定义候选配置通道。PDF原件、AI请求响应、语音和音频不走这些主题。MQTT不提供apply、confirm、NSH字符串或寄存器写入指令。

## 2. 连接与权限

- 远程候选接入使用MQTT over TLS，校验Broker身份；每设备独立凭证与ACL。现有公网1883明文链路不开放候选接入。
- 受控局域网可在显式测试构建中验证协议，使用测试凭证和真实人工确认，不把测试配置当作远程交付。
- 手机不持有设备或服务端Broker凭证。云侧先校验用户与网关绑定，再由专用配置服务发布；云侧LLM只输出数据，不能直接访问Broker。
- 设备只订阅自己命名空间的配置请求，只发布自己的配置状态；配置服务具有经用户绑定授权的设备范围，遥测看板保持只读。
- ACL隔离请求与状态方向。payload中的设备或用户标识不能代替身份认证；完整凭证不进入消息、界面或日志。

## 3. 主题与关联字段

根路径沿用 `vg/{device_id}`。新增两个主题均为QoS 1、retained=false；设备拒绝收到的retained配置请求。PUBACK只代表消息传输确认，手机必须依据板端状态判断结果。

| 主题 | 方向 | 用途 |
|---|---|---|
| `config/request` | 配置服务→板端 | open、put、cancel、query |
| `config/state` | 板端→配置服务 | 受理、配置校验结果、等待确认及最终状态 |

所有消息包含 `schema_version=1`、`device_id`、`req_id`、`task_id`、`op`。`req_id`、`task_id` 为不超过64字节的ASCII标识。未知版本、未知操作或多余的执行字段直接拒绝，不解释为shell命令。

open请求必须关联当前设备 `boot_id`。设备验证无其他配置会话后生成随机、不可复用的 `session_id`，返回当前已确认表的 `base_hash`、当前候选revision和租约。其余请求必须携带同一 `boot_id`、`session_id`；设备重新启动后旧会话全部失效。session_id仅作关联与防重放，不代替TLS/ACL。

设备不接受open请求携带候选内容。重连先query当前任务，核对boot_id和租约，禁止自动重放旧候选。open重复请求必须返回原会话或已结束结果，不延长租约或新建会话。

状态额外包含 `state_seq`、`revision`、`candidate_hash`、`base_hash`、`confirmation_id`、`state`、`error_code`、`retryable`、`uptime_ms` 和 `time_quality`；尚未产生的字段为null。`state_seq`在会话内单调递增，云侧丢弃较旧状态，终态不被晚到的等待状态覆盖。confirmation_id由板端生成，仅关联本地确认界面，不作为远程确认凭证。协议不提供test操作或试读字段。

### 候选put

- 第一次put要求 `revision=1`、`expected_revision=0`；后续每次完整替换候选要求 `revision=当前revision+1`，并携带 `expected_revision=当前revision`。新版本必须重新发送完整候选，不发送局部修改指令。
- 最近一次修改以板端受理的revision为准，不按消息到达顺序、墙上时间或文件修改时间猜测。并发编辑只有一份能通过expected_revision检查。
- 接收、验证、写入候选成功后才推进revision。旧版、跳号、版本冲突不覆盖当前候选；相同req_id和相同内容返回原结果，相同req_id但不同内容拒绝。
- 初版仅支持新增设备。以base_hash指向的完整已确认表为基础合并，保留现有点位；已有从机地址、重复点位id、空新增表、超过32点或能力不支持均拒绝。修改已有设备和清空运行表仍留给原NSH流程。
- 每点保留名称、FC、原文地址与协议地址、数量、类型、倍率、偏移、单位、PDF标识、型号、页码、原文依据。没有偏移时显式为0。仅接受实际固件支持的字段组合；当前仅int16/uint16，不支持的32位、浮点、字序或非零偏移不得静默降级。
- 测量范围不自动生成告警阈值；阈值只来自用户显式输入，界面标明来源。总线保持9600，地址与参数不匹配直接报错，不自动扫描或改地址。

### 内容摘要

请求中的 `candidate_json` 是UTF-8 JSON字符串，`payload_sha256`针对该字符串解码后得到的原始UTF-8字节计算，包含点位及来源。设备核验后解析，并保留同一原始字节串供审计；不依赖两端JSON重排后能产生相同摘要。

设备将合并后的完整运行表序列化，生成 `candidate_hash`，并保存这份确定的待提交内容。`base_hash`指向当前持久化运行表的原始字节摘要。本地确认绑定revision、payload_sha256、candidate_hash和base_hash，避免既有表变化造成覆盖。

## 4. 配置校验与本地确认

主流程：`opened → validating → awaiting_local_confirm → committing → applied`。失败分别返回可重试的原状态或终态failed；取消与租约超时进入cancelled或expired。validating只检查配置数据，不打开RS485、不发Modbus请求。

1. put进入确定性配置校验：身份与会话、字段范围、从机地址、支持类型、重复id、点数、容量、来源及合并冲突均须通过。校验和存储在后台有界执行，不在MQTT接收回调中阻塞；本步骤不进行通信试读。
2. 校验通过且候选存储成功后，板端生成confirmation_id，绑定当前revision及内容摘要，进入等待确认并弹出二次确认界面。校验失败不弹窗，原因仅回传手机，原运行表不变。
3. 有效新版put受理后，旧confirmation_id立即失效并关闭旧界面；新版重新配置校验通过后弹出新确认。旧校验的迟到结果不能覆盖新版。若原已确认表变化，任务结束并要求重新open。
4. 板端二次确认界面只展示本次确认所需的目标设备、新增/保留点位、类型、倍率、单位和手册页码，不显示试读值或在线结论，提供确认添加和取消。确认按钮只绑定屏幕正在展示的revision、candidate_hash和confirmation_id，不读取另一个可变的最新候选。
5. 用户在板端按确认添加，确定性代码在提交互斥区重新校验会话、租约、base_hash、版本和confirmation_id，成功落盘后才更新内存/代次、通知MQTT并进入applied，随后由周期采集读取新增点位。两次点击只提交一次；正常采集失败按现有离线/告警规则处理，不把配置添加成功写成采样成功。
6. 不接受任何MQTT确认指令。手机上传、云侧解析、ASR文本或Agent输出均不能替代上述操作。板端二次确认界面提供取消；手机可按协议取消尚未提交的任务。

远程配置的进度、阶段、等待、成功与失败状态只在手机显示；板端不增加状态栏标记、阶段页面或结果提示。open及配置校验进行中保持现有页面，手机下发的候选配置校验通过后弹出二次确认。取消、断网、候选更新或租约过期时关闭失效确认界面，结果回传手机；新版重新校验后才可弹出确认。进入提交后关闭确认界面，最终结果仅回传手机，不在板端展示提交进度或完成提示。现有监测页面与本地告警继续正常工作，确认界面不得遮挡本地告警。

## 5. 上限、失败与恢复

以下是首版建议预算，实施时必须测量内存、MQTT收包与界面表现后确认，当前不宣称固件已支持。

- 单网关仅1个配置会话和1份活动候选；校验中的新版与旧候选最多短暂共存各1份，旧校验结果不得复活旧确认。任一配置请求的完整UTF-8 payload不超过16KiB，单条状态不超过4KiB；错误摘要有界，标明是否截断，截断不影响拒绝结果，不附带试读数据。
- 候选合并后最多32点；具体字段限制取现有点表校验器与新增传输限制的较小值，不截断字段。原文过长时云侧要求精简引用，不在板端自动截断。
- 会话租约10分钟，以板端单调时钟计时且不自动延长；过期关闭确认界面并要求重新open，不自动添加。
- 单会话最多32个不同req_id；状态query每秒最多1次，越限不执行操作。缓存本会话请求摘要和结果，重复请求不重复I/O或弹窗。终态保留用于查询，直到新会话建立；更早会话返回unknown_task，不重执行。
- 配置会话或存储忙时云侧间隔1、2、4秒最多重试3次；同req_id重传只获取原结果，明确可重试错误后的新尝试使用新req_id。重试仍服从租约和次数预算，禁止无限重试。

| 情况 | 处理 |
|---|---|
| 错网关、鉴权失败、旧boot/session、retained消息 | 拒绝，不写候选、不弹确认；返回或记录相应错误，避免回传敏感内容 |
| 旧revision、重复请求、迟到校验或状态 | 返回当前状态或原请求结果；内容冲突报revision_conflict/req_conflict，不覆盖新版、不重复弹窗 |
| 缺必要字段、不支持格式、地址冲突、容量不足 | 返回具体点位和原因；原运行表及已受理候选不变 |
| 配置校验失败、配置入口忙或存储异常 | 手机展示原因，失败候选不弹确认；原运行表不变，按错误类型决定是否允许重试 |
| MQTT断线或取消发生在提交开始前 | 使confirmation_id失效并关闭确认界面；保留运行表。重连需重新open或query终态，不能自动恢复确认 |
| 取消、租约过期与确认并发 | 在同一状态锁下决定顺序；进入committing前可取消，之后返回too_late并查询实际提交结果 |
| 落盘失败或空间不足 | 不切换内存表，不报applied；进入failed，返回storage_error并按存储层实际恢复结果报警 |
| 已进入committing后断网 | 完成或失败由板端确定；网络恢复query实际终态，不能因超时再次提交 |
| 板端重启 | 旧会话和本地确认一律失效，先校验持久化运行表；只能报告实际加载结果，不能凭云侧已发送状态补报成功 |

applied终态回执包含新运行表hash。确认前先保存有界提交记录（task/session/revision/预期表hash），启动后对照实际运行表；记录丢失、损坏或表不完整时返回recovery_unknown并要求核对，不盲目补交。此记录不等同于FAT掉电原子性或完整双槽保护，异常恢复必须板验。

## 6. 与NSH共存

新增接口实施前NSH不变：试读展示后停下来等人，再单独发送apply。现行NSH没有试读版本强制检查。

实施远程接入时必须同步增加所有配置入口的会话互斥。远程配置会话活动期间，NSH候选编辑、试读、apply、abort与扫描生成候选返回明确busy，不共享文件覆盖候选；已确认表查询继续可用。NSH存在未结束候选时拒绝远程open，不删除该候选。通过手机或板端二次确认界面取消，或会话超时结束后才允许切回NSH。

远程候选使用独立的受保护存储，原NSH apply不得读取它。NSH锁检查与提交必须处在同一临界区，避免先检查后提交的竞争。板载Agent对两条入口都没有访问权限。

## 7. 后续实施与验收

先实现主机侧状态机与协议校验，再接入MQTTS收包/权限、后台配置服务与板端预览确认；板测中的现有固件不因本文而变化。手机及云侧可先使用明确标注的模拟器联调。

必须覆盖：完整新增、未确认/取消不生效、重复/乱序消息、候选修改使旧确认失效、字段/能力校验失败、错网关、超限、NSH竞争、断网/租约过期、落盘失败、确认与取消竞争、重启后核对实际运行表。确认前不产生新增候选的Modbus请求；从站离线也可在配置有效并人工确认后添加，之后真实采集失败与离线状态单独取证。检查板端仅弹出二次确认、不出现远程配置状态提示，失效确认及时关闭；所有进度和结果在手机展示。运行采集、告警、界面与MQTT已确认表必须一致，并验证云侧及Agent均无法代确认。
