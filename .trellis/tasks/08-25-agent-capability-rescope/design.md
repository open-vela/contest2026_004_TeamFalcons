# 设计：新 Agent 能力场景与配套边界

> 本文是即将写入 `VelaGuard_项目手册.md` 与 `VelaGuard_推进方案.md` 的实质草稿。
> 依据 `prd.md` 的 D1–D4 决策与 F1–F6 事实。

---

## 1. 新的分工口径

替换手册 §4.2 的表。一句话：**确定性算法解决「这是什么数」，Agent 解决「这是什么」。**

| 问题 | 性质 | 由谁做 |
|---|---|---|
| 总线上有哪些从站？ | 穷举搜索 | 确定性算法 |
| 哪些寄存器可读？ | 穷举探测 | 确定性算法 |
| 这几个寄存器是什么数据类型和字序？ | 约束求解 | 确定性算法 |
| 当前链路质量如何？ | 统计 | 确定性算法 |
| 链路故障归因 | 分类 | 规则库（原 §5.7 决策表） |
| **这个寄存器是什么物理量？单位是什么？** | **开放世界知识** | **Agent** |
| **正常区间与告警阈值该设多少？** | **领域常识 + 采样证据** | **Agent 建议 + 人确认** |

### 为什么这次的 Agent 是不可替代的

- 「40010-40011 = CDAB float32 = 12.34」是可计算的，算法必胜
- 「这是冷却水流量，单位 m³/h，正常区间 8–15」需要知道设备型号代表什么、工业流量计的典型量程、这类设备的寄存器布局惯例——**训练语料中大量存在的开放世界知识，算法无从下手**

对比原「485 故障归因」场景：那是个可枚举的分类问题（手册 §5.7 自己列了 9 条决策表），LLM 反而不如决策树可靠。本场景的问题空间是开放的，无法枚举，这才是 LLM 的主场。

## 2. A 场景：点表语义化

### 2.1 输入线索（按可靠性排序）

1. **设备标识寄存器**——Agent 主动探测常见位置读取 ASCII 型号串。设备自报，最可靠，且不依赖人工输入
2. **上位机输入的型号 / 铭牌信息**——人工提供（见 §4）
3. **寄存器地址布局惯例**——如 4xxxx 起连续块的常见语义模式
4. **多次采样的值域、变化率、量纲数量级**——确定性证据，用于证伪假设

### 2.2 ReAct 循环：Agent 用只读工具验证自己的语言学猜测

```text
假设：40001 是温度（值 824，×0.1 = 82.4，落在工业温度典型区间）
→ probe_register_block 读相邻寄存器，看是否有配套的上下限寄存器
→ sample_register 连续采样 10 次，看变化率是否符合温度的热惯性（缓变）
→ 若变化率剧烈跳变，推翻温度假设，改猜瞬时流量或转速
→ 重新采样验证 → 收敛，输出候选语义
```

这个循环比原方案的「设计诊断实验」更自然：**假设来自 LLM 的知识，验证手段来自确定性工具**，两者各司其职。

### 2.3 工具集（全部只读）

沿用原设计的多数工具，新增三个语义验证专用工具。

| 工具 | 状态 | 作用 |
|---|---|---|
| `modbus_scan(addr_range, baud)` | 沿用 | 扫描存活从站 |
| `modbus_read(addr, fc, reg, count, timeout_ms)` | 沿用 | 单次只读请求，功能码限 01/02/03/04 |
| `probe_register_block(addr, start, count)` | 沿用 | 探测寄存器块可读性 |
| `get_point_table(addr)` | 沿用 | 读取当前点表 |
| `get_bus_topology()` | 沿用 | 读取已知从站清单与参数 |
| `read_device_identification(addr)` | **新增** | 探测常见设备标识寄存器位置，读出 ASCII 型号串 |
| `sample_register(addr, reg, count, times, interval_ms)` | **新增** | 连续采样，返回值序列与变化率统计。语义验证的核心工具 |
| `get_decoded_candidates(addr, reg)` | **新增** | 取确定性求解器给出的数据类型 / 字序候选 |

**移除**：`set_probe_baudrate(baud)`（属于故障诊断场景，本场景不需要改波特率）。

### 2.4 沙箱约束：完全沿用原 §2.3

这是原方案中最有工程含量、最值得保留的部分，一条不改：

- 只注册只读功能码 `0x01` `0x02` `0x03` `0x04`
- 写功能码 `0x05` `0x06` `0x0F` `0x10` 在工具集里根本不存在
- 从站地址、寄存器地址、寄存器数量、超时时长、采样次数均有硬上界，越界直接拒绝
- 单位时间请求数限流
- 只在语义标注会话期间激活，会话结束工具集失效
- 每次工具调用写结构化审计日志

注意事项沿用手册 §11.1：`tool_guard.c` 只做禁用检查、大小检查和限流，**不做 JSON Schema 运行时校验**，参数越界必须在自定义工具内部自行拦截。

### 2.5 Skill 替换

- **删除** `rs485_fault_triage.md`
- **新增** `modbus_register_semantics.md`，路径 `/data/agent/skills/`

内容骨架：

1. 任务目标与安全约束（只读、限流、不得建议写寄存器）
2. 可用工具清单与各自代价（扫描慢、连续采样占用总线时间）
3. 常见工业设备的寄存器布局惯例（温湿度变送器、电表、流量计、变频器）
4. 从值域 / 变化率 / 量纲反推物理量的判据：热惯性量（温度）缓变、瞬时量（流量、功率）可突变、累积量（电能、累计流量）单调递增、状态量取离散值
5. 假设验证的实验设计：如何用一次连续采样区分「温度」与「压力」
6. 何时承认无法确定，写入 `unresolved`
7. 输出格式约定

### 2.6 输出 schema（供板端校验）

```json
{
  "slave_addr": 5,
  "points": [
    {
      "reg": 40010,
      "count": 2,
      "data_type": "float32",
      "word_order": "CDAB",
      "semantic": "冷却水流量",
      "unit": "m3/h",
      "scale": 1.0,
      "normal_range": [8, 15],
      "suggested_alarm": { "high": 18, "low": 5 },
      "evidence": [
        "设备标识寄存器读出 'XY-800 FLOWMETER'",
        "连续 10 次采样变化率 0.3%/s，符合流量的连续性"
      ],
      "confidence_basis": "device_id_match"
    }
  ],
  "unresolved": [],
  "source": "agent"
}
```

沿用原设计的两条决策，理由不变：

- **不含 `confidence`**——LLM 自报置信度不可信，会诱导现场人员误判。改用 `evidence` 列出实际观测证据，另加 `confidence_basis` 枚举说明依据来源（`device_id_match` / `range_inference` / `layout_convention` / `guess`），让人自己判断
- **不含任何写操作字段**——Agent 只产出候选，激活须经 Local Confirmation

### 2.7 主动 + 执行场景（赛道 C9 硬要求）

原方案是「阈值主动」，新方案改为「**事件主动**」：

```text
总线扫描完成（事件）
→ 确定性求解器产出无语义的候选点表
→ 自动启动语义标注会话（无需人工点按）
→ Agent 调用 read_device_identification 尝试让设备自报型号
→ 逐点提出语义假设，用 sample_register 采样验证，ReAct 循环上限 10 轮
→ 收敛出带单位、量纲、建议阈值的候选点表
→ 推到 LVGL 屏幕等待 Local Confirmation
→ 确认后落盘并进入采集循环
```

`BOUNDARY.md:94`（C9）要求「timer / threshold / event / context-driven」四类之一，**事件主动完全合规**。

### 2.8 可证伪验收判据（替换手册 §14.2）

对标原判据的形式——不是演示一次成功，而是一个可能失败的数字：

> 用 N 个真实 Modbus 从站（覆盖温湿度、电表、流量计等不同类型）共 M 个寄存器点位，记录 Agent 语义标注中被人工判定「物理量正确且单位正确」的点位比例，以及全过程写操作触发次数。

目标草案：**≥ 60% 点位语义与单位正确，写操作触发次数 = 0，且所有未确定点位显式列入 `unresolved` 而非瞎猜。**

比原判据更好的地方：**可离线复现**。录下从站响应后回放即可重跑，不需要每次切跳线、改从站波特率。这直接解决了原方案「验证成本极高」的问题。

## 3. 原诊断能力的去向

不是删除，是**降级并转移**：

- 手册 §5.7 的 9 条「现象 → 归因」决策表**保留**，实现为确定性规则库，排在阶段 2
- 帧级质量统计（§5.3）**保留**，它是告警与规则库的证据来源，也是阶段 0 地基
- 「Agent 自主设计诊断实验」**移除**，理由写入推进方案 §2 的被推翻决策章节（prd.md Background 五条）
- 链路劣化告警**保留**，由规则引擎产生，不再自动拉起 Agent 会话

净效果：诊断能力从「Agent 招牌」变成「规则库的确定性能力」，反而**不再依赖网络**，断网降级口径因此可以简化。

## 4. 上位机设计边界

### 4.1 形态与通道

- 形态：轻量本地 Web GUI——Python 后端持串口，浏览器前端
- 通道：**USB CDC / 串口**，JSON-over-serial，带长度前缀 + CRC
- 板侧新增 `host_link` 模块，对接 `config_store` / `point_table` / `event_store`

### 4.2 功能范围

设备型号 / 铭牌线索输入、表格化点表编辑、告警规则表单、实时值监视、配置下发。

### 4.3 三条不可逾越的边界

1. **运行期不必需**（守 V1，`BOUNDARY.md:107`）：断开上位机后采集、帧统计、告警、日志、安全默认态全部照常。上位机是配置期工具，不是 PC sidecar
2. **只创作，不激活**（守 V5，`BOUNDARY.md:111` 与手册 §2.3）：上位机可以编辑配置，但**激活必须经屏幕上的 Local Confirmation**。否则 Local Confirmation 边界被架空
3. **手册 §2.1 需修订**：USB CDC / UART 的定性从「仅开发调试和救援通道，不是正式运行链路」改为「配置期正式通道 + 救援通道」

### 4.4 它顺带解决的问题

上位机为手册 §6.1「屏上不做任何编辑」补上了此前缺失的承接落点——配置创作是办公室的事，屏幕只负责看和确认。这个原则此前无处落地，现在闭环了。

## 5. 语音：SAI 探针设计

### 5.1 定位

照搬推进方案 §1「先证伪最大的未知」与 §4 ai_agent 探针的做法。**20 h 封顶**，探针通过前不把完整语音链路写进计划。

### 5.2 唯一目标

证明 STM32H750B-DK 上 SAI + WM8994 能出声。

### 5.3 刻意排除

- 不碰 PDM MEMS 麦克风（模拟麦与 line out 共用 SAI 链路，PDM 是另一条通路）
- 不碰 ai_agent 的 `src/voice/` 管线（避免叠加 Vela media framework 在 M7 上的未知风险，见 prd.md F4）
- 不碰云端 ASR / TTS
- 不碰唤醒词

### 5.4 实施路径

1. 移植 `nuttx/arch/arm/src/stm32f7/stm32_sai.c`（约 1,666 行）到 `stm32h7/stm32_sai.c`，补 `stm32h7/Kconfig` 的 SAI 子选项（当前 `Kconfig:685-687` 只有一个空 bool）
2. 板级 `stm32h750b-dk/src/stm32_wm8994.c`，参考同 codec 的 `stm32f746g-disco/src/stm32_wm8994.c:256-268`
3. `include/board.h` 补 `GPIO_SAI*` 引脚宏（参考 `stm32f746g-disco/include/board.h:529-538`）
4. `stm32_bringup.c` 挂接，参考 `stm32f746g-disco/src/stm32_bringup.c:148-154`
5. defconfig 启用 `CONFIG_AUDIO` + `CONFIG_DRIVERS_AUDIO` + `CONFIG_AUDIO_WM8994` + `CONFIG_STM32H7_SAI`

### 5.5 成功判据

绿色 line out（CN9）或外接喇叭（CN17/CN18）能播出一段可辨识的 PCM/WAV。

### 5.6 出口条件

- **通过**：规划完整语音输入输出（输入解决型号线索，输出服务阶段 2 的 B 场景告警播报），并作为上游 PR 交付
- **不通过**：语音移出计划。`BOUNDARY.md:65`（C11）靠 LVGL 命中「图形」已足够，多媒体非必需

### 5.7 顺带更正的事实

手册 §2.4 / §3.2 与推进方案 §2.3 写「WM8994 codec 树内无驱动，需自写」——**错误**。`nuttx/drivers/audio/wm8994.c` 早已存在，缺的是 STM32H7 SAI 驱动与板级接线（prd.md F2）。这条错误直接导致 v2 把语音判为「投入产出比极低」，结论需要重估。
